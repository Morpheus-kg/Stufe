# German Trainer — CONTRACT v3 (multi-user isolation + calm redesign)

Extends CONTRACT v1 and v2. Where v3 conflicts with them, v3 wins. Project state before v3: single-user data model, plus an unplanned authentication layer (table `users`, roles, `server/routes/admin.js`, token with role) that does NOT isolate data. v3 has two parts: **A** makes the app truly multi-user (each user has their own cards, progress, texts, settings, statistics, AI usage, optionally their own AI keys), **B** is a visual redesign in a calm minimalist style (CSS and markup only, no logic changes).

---
# PART A — Multi-user isolation

## A0. Principles
1. Identity comes only from the authenticated session (`req.user.id`). Never from body, query or URL, except in admin routes that explicitly manage other users.
2. Every row of user data belongs to exactly one user (`user_id`). Every SQL statement that touches such a table filters or inserts `user_id`. A foreign id behaves exactly like a missing one: HTTP 404, never 403 (no existence leaks).
3. Fail loudly: after migration, `user_id` columns have NO default, so a forgotten insert errors instead of silently creating orphan rows.
4. No new npm packages (Node `crypto`, `util.promisify`).
5. Never log passwords, tokens, API keys, or user texts.

## A1. Users and authentication
`users` columns (migration 003 adds missing ones): `id`, `username`, `role ENUM('admin','user')`, `password_hash`, `created_at`, plus `must_change_password TINYINT(1) NOT NULL DEFAULT 1`, `token_version INT NOT NULL DEFAULT 0`, `disabled TINYINT(1) NOT NULL DEFAULT 0`, `ai_mode ENUM('shared','own','off') NOT NULL DEFAULT 'shared'`, `last_login_at DATETIME NULL`, `last_active_day DATE NULL`. Username rule (lowercased on input, unique): `^[a-z0-9][a-z0-9_.-]{2,31}$`. Password: 8..128 characters.

- **Hashing**: `crypto.scrypt` ASYNC (`promisify`), per-user salt, `timingSafeEqual`, format `<salt_hex>:<hash_hex>` as already implemented (keep compatible with existing hashes).
- **Token** (cookie `sid`, httpOnly, SameSite=Lax, Secure in production, 30 days): `v2.<expMs>.<nonce>.<userId>.<tokenVersion>.<hmac>`. No role inside. Old `v1` tokens become invalid (everyone logs in again once).
- **`requireAuth`**: verifies the HMAC and expiry, then loads the user from the database (in-process cache, 30 seconds, cleared whenever a user is changed or deleted) and rejects with 401 when the user is missing, `disabled`, or the token's `tokenVersion` differs. Sets `req.user = {id, username, role, must_change_password, ai_mode}`. Updates `last_login_at` on login and `last_active_day` at most once per day.
- **`requireAdmin`**: uses `req.user.role` from that fresh lookup (a demoted admin loses access immediately).
- **Login** `POST /api/auth/login {username, password}`: unknown user and wrong password return the same 401 `INVALID_CREDENTIALS` and take comparable time (verify against a precomputed dummy hash for unknown users). Rate limits (in memory): 20 attempts / 15 min per IP and 8 / 15 min per lowercase username.
- **`APP_PASSWORD`** is no longer a login method. It is only used by migration 003 to create the first admin (`owner`) when no admin exists. If there is no admin and no `APP_PASSWORD`, the server refuses to start with a clear message. Recovery: `scripts/admin_cli.mjs` with `create-admin <username>` and `reset-password <username>` (prompts or prints a generated temporary password locally, sets `must_change_password=1`, bumps `token_version`).
- **Forced password change**: while `must_change_password=1`, every `/api/*` route except `/api/auth/*`, `GET /api/me` and `PUT /api/me/password` returns 403 `{error:{code:'PASSWORD_CHANGE_REQUIRED'}}`.
- **Self-service password** `PUT /api/me/password {current_password, new_password}` -> 204: verifies the current password, stores the new hash, clears `must_change_password`, bumps `token_version` and sets a fresh cookie for the current session (other sessions die).
- Temporary passwords generated by the server: 12 characters from an unambiguous alphabet, shown to the admin exactly once.

## A2. Data model
All of these tables get `user_id INT UNSIGNED NOT NULL`: `cards, card_state, review_log, sentences, staging_cards, settings, daily_stats, import_runs, texts, text_attempts, translation_sets, writing_tasks, writing_attempts, speaking_attempts, number_attempts, exam_log, activities`. `ai_usage` gets `user_id` in its primary key. Global tables (no `user_id`): `ai_cache`, `schema_migrations`, `users`.

Key changes:
- `cards`: replace `UNIQUE uq_dedupe(dedupe_key)` by `UNIQUE uq_user_dedupe(user_id, dedupe_key)`; indexes `(user_id,pos)`, `(user_id,topic)`, `(user_id,enriched)`. Keep `dedupe_key` collation `utf8mb4_bin`.
- `card_state`: primary key stays `(card_id, mode)`; add index `(user_id, due)`.
- `review_log`: replace `UNIQUE uq_uuid(client_uuid)` by `UNIQUE(user_id, client_uuid)`; indexes `(user_id, local_day)`, `(user_id, card_id, mode)`.
- `staging_cards`: indexes `(user_id,status)`, `(user_id,dedupe_key)`.
- `settings`: primary key `(user_id, key_name)`.
- `daily_stats`: primary key `(user_id, day)`.
- `ai_usage`: primary key `(day, user_id, provider, feature)`.
- Other tables: add a leading-`user_id` index matching their main query (`texts(user_id,kind,created_at)`, `activities(user_id,local_day,kind)`, `number_attempts(user_id,local_day)`, `exam_log(user_id,taken_on)`, `translation_sets(user_id,created_at)`, `writing_attempts(user_id,local_day)`, `speaking_attempts(user_id,local_day)`, `import_runs(user_id)`, `sentences(user_id,created_at)`).
- New table `user_keys(user_id INT UNSIGNED NOT NULL, provider VARCHAR(20) NOT NULL, ciphertext VARBINARY(512) NOT NULL, iv VARBINARY(12) NOT NULL, tag VARBINARY(16) NOT NULL, updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP, PRIMARY KEY(user_id, provider))`.
- `db/schema.sql` and `db/schema_v2.sql` are updated to these final shapes so fresh installs are correct; migrations stay idempotent.
- No foreign keys to `users`; user deletion is an explicit transactional delete in code (A6), because the existing FKs (`card_state` -> `cards`, `text_attempts` -> `texts`) already cascade within a user.

## A3. Migration `server/migrations/003_multiuser.js` (idempotent, safe on MySQL 8 and MariaDB)
New helpers in `server/migrate.js`: `indexExists`, `dropIndexIfExists`, `addIndexIfMissing`, `primaryKeyColumns`, `setPrimaryKey(table, cols)` (all via information_schema). Steps, each logged and wrapped so a failure names the table:
1. Ensure the new `users` columns exist.
2. Resolve the owner: first admin by id; if none, create `owner` (admin) with the hash of `APP_PASSWORD` and `must_change_password=1`; if neither exists, throw a clear error.
3. For each user-owned table: add `user_id INT UNSIGNED NOT NULL DEFAULT 0`, `UPDATE t SET user_id = <owner> WHERE user_id = 0`, then `MODIFY user_id INT UNSIGNED NOT NULL` (drops the default).
4. Apply the key and index changes of A2 (drop old unique indexes only after the new ones exist).
5. Create `user_keys`.
Acceptance for the migration: on a database with v1+v2 data, row counts per table before and after are equal, every row has `user_id = owner`, the second run changes nothing, and the app works for the owner exactly as before.

## A4. Scoping rules and enforcement
- R1 `req.user.id` is the only identity source. R2 every statement on a user-owned table contains `user_id` (WHERE, JOIN condition or INSERT column). R3 lookups by id: `WHERE id = ? AND user_id = ?`, absent -> 404. R4 joins filter the user-owned side(s) (e.g. `card_state s JOIN cards c ON c.id = s.card_id AND c.user_id = ?`). R5 import, export, restore, enrich, plan, skills, stats, session, reviews, texts, translate, retell, speaking, writing, numbers, exam, staging, lookup are all per user. R6 in-memory state (enrich lock, rate limiters, caches, debounce) is keyed by user id; the enrichment lock is per user. R7 `restore?mode=replace` deletes only the caller's rows. R8 `INSERT IGNORE` and `ON DUPLICATE KEY` statements include `user_id` in the key.
- `scripts/check_scope.mjs` (static, no dependencies): extracts every SQL string in `server/` (template literals and quoted strings passed to `query`, `conn.query`, `tx`), and for each statement mentioning a user-owned table requires the token `user_id`. Allowlist only with an inline marker `/* scope-ok: reason */` (migrations, schema, admin cross-user queries marked `/* admin-scope */`, `ai_cache`, `users`). Exit code 1 on violations. Added as `npm run check:scope`.

## A5. AI quotas and personal keys
- Caps: `AI_DAILY_CAP_<FEATURE>` now applies PER USER per day (unchanged names and defaults). New optional `AI_GLOBAL_CAP_<FEATURE>` limits the sum over all users (unset = unlimited); when reached: 429 `AI_CAP` with a message that the shared limit is exhausted for today.
- `users.ai_mode`: `shared` (server keys, caps apply), `own` (only the user's own keys, no caps), `off` (503 `AI_UNAVAILABLE`, message "ИИ отключён администратором").
- **Personal keys**: `PUT /api/me/keys {provider:'groq'|'gemini'|'openrouter', key(8..200)}` -> 204; `DELETE /api/me/keys/:provider` -> 204; `GET /api/me/keys` -> `{groq:bool, gemini:bool, openrouter:bool}`. Keys are encrypted with AES-256-GCM (random 12-byte iv, auth tag stored), key derived by HKDF-SHA256 from env `KEYS_SECRET` (at least 32 characters; if missing the three endpoints return 501 with a Russian message). Keys are never returned, logged or echoed in errors; deleted with the user.
- `server/ai/llm.js`: `chatJSON` requires `userId`; key resolution per provider: the user's own key if present (unless `ai_mode='off'`), else the server key only when `ai_mode='shared'`. Models still come only from env. `GET /api/ai/providers` reports availability from the user's effective keys. `ai_usage` rows carry the user id. `ai_cache` stays global (content-addressed).
- `GET /api/ai/usage` returns the caller's own usage and caps.

## A6. API additions and changes
- `GET /api/me` -> `{id, username, role, must_change_password, ai_mode, keys:{groq,gemini,openrouter}, created_at}`.
- `POST /api/me/starter-deck` -> `{copied, skipped}`: copies the active cards (all text fields, `enriched` and `check_flag`, no progress) of the starter user (env `STARTER_USER`, default: the first admin) into the caller's deck, skipping duplicates by `(user_id, dedupe_key)`.
- Admin (`requireAdmin`, every handler re-validates input with zod):
  - `GET /api/admin/users` -> items `{id, username, role, disabled, ai_mode, created_at, last_login_at, last_active_day, cards, reviews_7d, ai_calls_today}` (counts only, never content).
  - `POST /api/admin/users {username, role='user', password?}` -> `{user, temp_password}` (generated when `password` is absent; `must_change_password=1`).
  - `PUT /api/admin/users/:id {role?, disabled?, ai_mode?, reset_password?:true}` -> `{user, temp_password?}`; any role, disabled or password change bumps `token_version` and clears the user cache.
  - `DELETE /api/admin/users/:id {confirm_username}` -> `{deleted:{table:count}}`: one transaction removes all user-owned rows and `user_keys`, then the user.
  - Guards: nobody can demote, disable or delete the last active admin; an admin cannot disable or delete themselves.
  - `GET /api/admin/usage` -> today and last 7 days of AI calls by user and feature, plus totals against caps.
- `GET /api/export` exports only the caller's data; `POST /api/export/restore` writes only into the caller's data.
- Registration stays closed: only admins create accounts.

## A7. Frontend functions (behavior only; styling comes from part B)
Login screen asks username and password. On `PASSWORD_CHANGE_REQUIRED` the app shows only a change-password screen. Profile screen (menu "Ещё"): username, change password, AI keys (write-only fields, shows "сохранён" state, delete), button "Взять стартовый набор", logout. Admin screen: user list with the stats above, create (temporary password shown once with a copy button), reset password, enable/disable, AI mode select, delete with typed username confirmation, usage panel. New API wrappers in `public/js/api3.js`: `me, changePassword, getKeys, putKey, deleteKey, starterDeck, adminUsers, adminCreateUser, adminUpdateUser, adminDeleteUser, adminUsage`. A failed request must never be retried in a loop.

## A8. Tests and checks
- `scripts/isolation_test.mjs` (integration, runs only against the database named in `MYSQLDATABASE` and refuses to run unless the name ends with `_test`): creates admin plus users A and B, seeds A in every domain (cards, reviews, staging, texts and attempts, numbers, exam, a translation set inserted directly, activities), then asserts for B: every list endpoint is empty, every `:id` of A's rows returns 404, A's `client_uuid` can be reused by B, B can import the same cards (dedupe is per user), B's export contains none of A's rows, plan and skills are empty, A's deletion removes only A's rows, forced password change blocks other routes, disabled users and old tokens (after password change) get 401, a demoted admin loses admin routes immediately, `APP_PASSWORD` no longer logs in, last-admin and self-guards work, AI usage rows are separate.
- `tests/auth.test.js` (no database): hash/verify, token issue/verify including version mismatch and tampering, username and password validation, rate limiter keys, key encryption round trip and tamper detection, temp password alphabet.
- `npm run check:scope` passes; `node --test` passes; migration test on a v1+v2 database with data (counts equal).

## A9. Acceptance
Migration verified on real data without loss; the owner sees exactly the previous data; a new user starts with an empty deck, defaults for settings and zero statistics; no endpoint exposes foreign data (isolation test green); all earlier smoke tests still pass for a user; no secrets in logs or files; `.env.example` lists `KEYS_SECRET`, `STARTER_USER`, `AI_GLOBAL_CAP_*` with empty values.

# PART B — Calm minimalist redesign

## B1. Principles
Quiet, text-first, lots of air. One accent color used sparingly, neutral everything else. One primary action per screen. Fewer boxes: sections separated by whitespace and hairlines, not by nested bordered cards. Content is the star (the word on the flashcard is huge, everything else is small and muted). No gradients, no heavy shadows, no emoji as UI chrome (simple inline SVG icons, 1.5 px stroke), no confetti. Motion is subtle (150 ms ease) and respects `prefers-reduced-motion`.

## B3. Components (`public/css/components.css`, class-based, reused by every view)
Button (primary = ink fill, secondary = hairline outline, ghost, danger; sizes md and lg; min height 44 px; one primary per screen), Card (surface, 1 px border, no shadow, used sparingly), List row (label left, value or chevron right, hairline separators, whole row tappable), Segmented control (difficulty, level, provider selects), Chip, Badge (provider, level), Input and Textarea (soft border, accent focus ring 2 px, visible label above), Progress bar (4 px, accent), Ring (stats), Bottom sheet (only element allowed a shadow), Toast, Empty state (one sentence and one action), Skeleton loader, Section header (small muted uppercase label). Icons: one `public/js/ui/icons.js` module exporting inline SVG strings, used via `innerHTML` only with these constants (never with user data).

## B4. Layout and navigation
Content column max width 640 px, centered, 16-20 px side padding, 24-32 px between sections. Bottom navigation: Today, Words, Practice, Stats, More (icon plus label, no floating buttons over content). The floating theme button is removed: theme moves to Settings (Auto, Light, Dark) using the existing `theme` setting, applied on boot from `localStorage` before first paint via `data-theme` on `<html>` to avoid a flash. The Practice screen layout already redesigned stays as is; only align its colors, radii and spacing to the tokens.

## B5. Screens (what changes)
- **Today**: plan as a plain list with check marks and minutes; one primary button "Начать карточки"; streak and daily minutes as two small numbers, no widgets.
- **Review**: nearly empty. Thin progress bar at the top, difficulty as a small segmented control, the term very large (`--fs-term`), translation and example muted, big input, hint link, feedback as a quiet inline message with a color tint and a text label (never color alone); the collapsed rating chip stays.
- **Words, Staging**: list rows instead of boxed cards; provider and level as badges; accept and reject as ghost buttons.
- **Texts, Reader, Listen, Lab**: reading typography (18 px, line height 1.7, max 62 characters per line); quiz options as list rows with a clear selected and correct/incorrect state.
- **Translate, Retell, Write, Speak, Numbers**: one task per screen, large textarea or input, a single bottom primary action, results as sections separated by hairlines (score as one large number, criteria as thin bars, errors as a list).
- **Stats, Skills**: few numbers, thin charts, ring only for retention, exam countdown as one line.
- **Settings, Profile, Admin**: grouped lists with section headers; destructive actions at the bottom in danger style with confirmation.
- **Login and forced password change**: centered single column, one field per row, no decoration.
- **Style guide** route `#/styleguide` showing every component in light and dark (kept in the app for later tweaks).

## B6. Constraints and process
1. CSS and markup only. Do not change logic, API calls, data attributes, element ids or any class name used by JavaScript selectors. Before renaming a class, search all usages (`querySelector`, `classList`, `getElementById`, `closest`, `matches`) and update both sides.
2. No new fonts, libraries, images or external requests (system font stack, inline SVG). Service worker keeps working: new CSS files are served from `/css/` (stale-while-revalidate, bump the cache version).
3. Files: `tokens.css`, `base.css` (reset, typography, layout), `components.css`, `app.css` (imports the three and holds only view-specific rules); remove dead rules.
4. Accessibility: visible focus rings, 44 px targets, labels linked to inputs (`for`/`id`), `aria-live` on feedback regions, no color-only meaning, contrast checked in both themes.
5. Work in batches: D1 system (tokens, base, components, shell, style guide, login, forced password change, profile), D2 learning screens (Today, Review and modes, Words, Staging, Texts, Reader, Listen, Lab), D3 the rest (Translate, Retell, Write, Speak, Numbers, Stats, Skills, Settings, Admin, Practice alignment).
6. Verification per batch: all routes load without console errors at 390 px and 1024 px width in light and dark; no horizontal scroll; `node --test` and `npm run check:scope` still pass; if a browser tool is available take a screenshot of each route and fix visible issues.
7. Deliver `DESIGN_NOTES.md`: token summary, component list, changed files, anything not verified.
